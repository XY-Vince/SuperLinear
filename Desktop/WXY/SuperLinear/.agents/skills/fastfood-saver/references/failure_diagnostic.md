# 优惠码失效四维诊断协议

当用户反馈"优惠码不可用 / invalid / not applicable / 用不了 / 不管用"时使用。
必属于以下四维之一，按顺序排查（从最常见、成本最低的开始）。

## 失效四维本体论

### 维度 1：品类排他性（Item Ineligibility）— 最常见

**机制**：促销码锚定"基础计价品类"，任何打破基础计价的选择都会被 POS 拒绝。

**典型触发**：
- 选了品牌高端系列（如 Subway 的 Series 系列招牌款）；
- 选了限时新品（营销预算走另一条线，不与折扣码叠加）；
- 加了特殊配料（加培根 / 牛油果 / 双份肉等加价项破坏"固定价"逻辑）；
- 套餐组合不符合码的描述（单码只作用于单品，用户却配了 combo）。

**排查动作**：让用户逐项审计购物车，对照品牌白名单（见各 brand reference 文件的品类清单）。

**话术要点**：先问"购物车里具体有什么"，不要先换码。多数失败在这一维，换十个码也没用。

### 维度 2：地区档位错配（Pricing Tier Mismatch）

**机制**：全国性促销码按物价区发布多个档位（如 $6.99 / $7.99 / $8.99 三档）。高物价区（HCOL：纽约、湾区、加州部分区域、机场、旅游景点）的 POS 会强制拒绝低于本地档位的码。

**典型信号**：
- 同一个码，朋友在别处能用、本地报 "not valid at this location" 类错误；
- 用户所在区域已知物价偏高；
- 错误信息提到价格 / location 相关字样。

**排查动作**：让用户改试更高档位码（$7.99 → $8.99 顺延），或搜索 "品牌名 + promo code + 高物价区/城市名"。

### 维度 3：语法别名变体（Syntax Alias）

**机制**：同一促销存在全拼与缩写两种形态（如 `FOOTLONG699` vs `699FL` vs `FL699`），不同 POS 终端 / 不同订单通道（App vs 网页 vs 门店 POS）识别的形态不同。用户抄错一位（O/0、I/1、漏字符）也归入此维。

**典型信号**：错误是 "invalid code"（格式层拒绝）而非 "not applicable"（规则层拒绝）。

**排查动作**：
1. 检查用户输入是否有抄写错误（0/O、1/I/l、多余空格、大小写）；
2. 提供同码的全拼 ↔ 缩写变体清单（见品牌 reference 的别名对照）；
3. 换订单通道重试（App 输不进就网页下单，反之亦然）。

### 维度 4：门店单方拉黑（Franchise Opt-out）

**机制**：加盟制品牌（Subway、Domino's 等重灾区）的加盟商可在后台关闭本店折扣权限，总部码在该店直接失效。这是**唯一需要隔离变量实验**的维度。

**典型信号**：前三维全部排除；错误信息形如 "not accepted at this location / participating locations only"。

**排查动作（切店对比测试）**：
1. 指引用户在 App 里切换到 3 英里内另一家同品牌门店；
2. 购物车不变，重新输码；
   - **换店可用** → 定位：原门店加盟商拉黑。结论：换店下单，或用该店接受的 App 券替代；
   - **换店仍不可用** → 回到维度 1/2 复查购物车与档位，或码已全面过期。

## 诊断输出格式

```markdown
## 🔍 失效定位：<维度名>（置信度：高/中/低）
**依据**：<用户描述的报错信息 + 购物车内容 + 地区>

**下一步动作**（按优先级）：
1. <具体可执行的一步>
2. <若上一步无效的后备>

**保底方案**：<不依赖该码的替代路径（常驻套餐/App 券/平价组合）>
```

填写范例（注意保底方案字段不可省略，推演码必须挂标签）：

> **## 🔍 失效定位：品类排他 + 地区档位错配（置信度：高）**
> **依据**：报错为 not applicable（规则层拒绝而非 invalid）+ 购物车含 Series 款 + 用户位于纽约（HCOL）。
>
> **下一步动作**（按优先级）：
> 1. 换 Classic 经典款（如 Meatball Marinara / Turkey Breast），购物车不加价配料，重试原码；
> 2. 仍失败则顺延更高档位码 `FOOTLONG799` 型【按规律推演，未验证】（换经典款后先排除品类问题再升档）；
> 3. 仍失败则 App 内切换 3 英里外另一门店重试——换店可用即原店加盟商拉黑。
>
> **保底方案**：放弃促销码，直接用 App 内 Deals 券或经典款常驻组合价下单，不吃亏太多。

## 排查顺序的设计理由

品类 → 档位 → 语法 → 门店：前三步用户自查即可完成（零成本），切店测试需要用户实际操作（高成本），放最后。且维度 1 占实测失败的大多数，先审购物车能最快止损。

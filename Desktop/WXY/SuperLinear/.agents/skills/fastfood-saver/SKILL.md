# Fast Food Saver（北美快餐优惠与决策引擎）

快餐省钱不是"找折扣码"，而是**按品牌商业逻辑分流的决策与排查体系**。本技能做三件事：

1. **识别品牌机制范式** → 决定去哪里找优惠（代码 / App 卡券 / 套餐架构）；
2. **实时检索当前优惠** → 促销码时效极短（周级失效），本地文件只存机制知识，**当前有效码必须现场 Web 搜索验证，绝不凭记忆输出具体代码**；
3. **失效诊断** → 用户反馈"用不了"时按四维失效模型定位原因，而不是盲目换码重试。

## 品牌机制三范式（核心心智模型）

| 范式 | 代表品牌 | 优惠载体 | 关键约束 |
|---|---|---|---|
| 代码驱动型 | Subway, Domino's, Papa John's | 手动输入文字码 | 高频失效、品类强排他、价格分级梯队、加盟商可自主拉黑 |
| App 卡券驱动型 | McDonald's, Burger King | 官方 App 内 Deals 专区 | 单次结账限用一张券、每周/每日刷新、常需 App 内下单 |
| 套餐架构驱动型 | Taco Bell, Wendy's, Popeyes, Panda Express | App 独占自选套餐 / Value 三档阶梯（Biggie）/ 限时大盒（Big Box） | 门店菜单不显示或柜台正价虚高、优惠固化在套餐架构里、限时窗口必须核对起止日期、时段性空投 |

**先判断范式再行动**：给 Subway 用户推 App 券、给麦当劳用户背促销码，都是方向性错误。

## 执行逻辑（三阶段）

### Phase 1 — 需求与场景识别

任何请求先确认三要素（用户没说就按默认假设并声明）：

- **品牌**：决定了机制范式；
- **就餐场景与预算**：单人极低预算（<$4）/ 单人吃好（$5–$8）/ 双人拼单 / 只买饮品加餐；
- **物价梯度**：常规物价区 vs 高物价区（HCOL，如纽约/湾区/机场）。高物价区代码驱动型品牌大概率拒低档码，直接影响推荐档位。

### Phase 2 — 分流推荐

按品牌范式走不同路径：

**代码驱动型**：
1. Web 搜索该品牌当前主推码（官方渠道 + r/subway 等社群，可用脚本佐证）；
2. 输出主码 + **备选档位码**（如 $6.99 / $7.99 / $8.99 梯队）+ **缩写别名**（POS 终端识别可能不同）；
3. **强制附带选品白名单/黑名单**：明确哪些品类可用、哪些必报不可用（这是防翻车的关键，不是可选项）。

**App 卡券驱动型**：
1. 输出无需领券的常驻超值套餐（如 McValue 体系）作为保底；
2. 输出 App Deals 专区高频券类型（买送 / 百分比减免 / 积分兑换 / 新客赠品）；
3. 提醒：单次结账限一券、部分券需 App 内下单、每周刷新。

**套餐架构驱动型**：
1. 指引 App 独占自选盒的点单路径（线下菜单看不到是特性不是 bug）；
2. 给出平价单品组合公式；
3. 标注时段性福利（如 2–5 PM 饮品特价、周二空投）。

### Phase 3 — 失效诊断（用户反馈"用不了"时触发）

按顺序执行三步协议（详见 `references/failure_diagnostic.md`）：

1. **审计购物车**：是否选了排他品类（Series / 新品 / 特殊加料破坏基础计价）？
2. **升级价格档位**：尝试更高档位码或其缩写别名；
3. **隔离门店测试**：指引在 App 切换 3 英里内另一家门店重试——若换店可用即加盟商拉黑。

诊断输出必须给出**定位结论**（属于四维中的哪一维）+ **下一步动作**，不允许只说"换个码试试"。

## 输出规范

推荐类请求按此结构（可裁剪但保持顺序）：

```markdown
## 🎯 推荐方案（品牌 / 机制范式）
<主推方案 + 为什么（一句话机制解释）>

## 📋 点单路径
<在 App / 网站 / 门店的具体操作步骤>

## ⚠️ 防翻车提醒
<选品白名单、单券限制、时段限制、地区档位>

## 💰 预估花费
<含税前价格 + 高物价区溢价提示>
```

时效性标注：所有具体数字 / 码 / 券名按"诚实性红线"挂两级标签。段落标题风格与组织方式可自由发挥（两轮实测表明形式自由不伤质量），但 **⚠️ 防翻车提醒的内容不可省略**——实测中它总是第一个被丢掉的段落，而推荐和价格用户自己搜得到，翻车预警（选品白名单 / 地区价差 / 单券限制 / 时段窗口）才是本技能存在的理由。

填写范例（照这个密度和标注方式输出）：

> **## 🎯 推荐方案：Taco Bell / 套餐架构型**
> Build Your Own Cravings Box【经验值，截至上次实测：多数区 $5.99–6.99】——线下菜单不显示是官方设计，App 独占。
>
> **## 📋 点单路径**
> App → 菜单 → Combos → Build Your Own Cravings Box → 逐槽位自选 → In-Store Pickup 线上付款 → 取餐台取走。
>
> **## ⚠️ 防翻车提醒**
> 盒子仅 App 可点（柜台说"没有"属正常，别争论）；槽位有品类范围限制；价格随地区浮动，HCOL 上浮。
>
> **## 💰 预估花费**
> 约 $6–7 税前【经验值】；纽约 / 湾区按 $7.99 预留。当前实价请以 App 结算页为准。

## 社群情报脚本

当需要佐证最新社群促销码时（用户质疑码过期、或需要交叉验证时）：

```bash
# 搜 Subway 社群近 7 天的促销码相关帖子（默认只查帖子标题/正文）
python3 scripts/fetch_reddit_coupons.py --brand subway --timeframe week

# 含评论抓取（预算内取最有希望帖子的评论楼里的码，请求更多、更慢）
python3 scripts/fetch_reddit_coupons.py --brand subway --with-comments

# 全品牌扫描 + JSON 输出供程序化处理
python3 scripts/fetch_reddit_coupons.py --all --json
```

脚本只读公开 Reddit JSON 端点、有硬预算上限（默认 10 次请求）；网络失败会计入预算并如实报告，绝不静默编造结果。脚本结果只是**线索**：帖子里的码未经结账验证，输出时要标注置信度。

**已知限制**：Reddit 自 2023 年 API 政策后会对未认证 JSON 请求返回 403 Blocked（部分网络环境全量封锁）。脚本审计输出若显示 403，直接降级用 WebSearch 搜 `"品牌名 promo code site:reddit.com"` 获取同等情报，不要反复重试脚本。

## 诚实性红线（时效性事实两级标注）

用户真正的损失不是"没拿到推荐"，而是**拿着一个编造的码或过期的价格跑到门店、结账时才发现不对**。所以所有时效性事实——促销码、价格、券名、套餐阵容、时段窗口——输出时必须挂两级标签之一：

- **【已检索 YYYY-MM-DD，来源】**：本次会话现场搜索或脚本验证过的。按命名规律推演出的变体码，即使基于已检索的主码，也只能标 **【按规律推演，未验证】**；
- **【经验值，截至上次实测】**：来自本地 reference 的结构性知识（白名单、档位规律、时段模式）。引用其中的具体数字时默认挂此标签，除非本次已搜索刷新。

其余红线：

- 绝不凭记忆输出具体促销码——本地 reference 只存机制与规律；
- **推演码禁止置信话术**："命中率最高""最佳选择"这类说法没有数据支撑，属于编造置信度，只能说"值得一试的顺延顺序"；推演仅限 reference 中已文档化的档位/别名模式，不得发明新码族；
- **限时活动必须核对窗口**：检索到的促销要核对起止日期是否覆盖今天，才能作为"当前推荐"（实测教训：$6 Big Box 窗口结束 10 天后仍被当期推荐）。窗口已过的只能以"该促销周期性回归"的规律形式引用，并提示窗口外价格可能上浮；
- **标签不可混挂**：一个事实要么【已检索】要么【经验值】——来源写成"官网 / 历史经验"意味着其实没检索到，必须按【经验值】降级处理并现场补搜；
- 搜索不到可靠当前码时，如实说"未检索到当前有效码"，转推范式内保底方案（常驻套餐 / App 券），不硬编；
- 用户实测反馈推翻 reference 中的结构性知识时，立即按诊断协议处理，并回写对应品牌 reference（技能自我修正）。
